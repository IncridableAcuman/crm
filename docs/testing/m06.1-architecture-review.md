> **Scope Constraint**: Architecture & documentation only. This pass wrote **no** Java, Liquibase, REST, or React code.

## 1. Executive Summary

`M06.1` now specifies the Inventory bounded context (`com.savdocrm.modules.inventory`) end-to-end: aggregates and invariants, an append-only stock ledger, location and warehouse balance projections, receiving/counting/adjustment/transfer workflows, reservations, WAC valuation, tenant isolation, `WAREHOUSE` RBAC, REST contracts, concurrency control, integration boundaries, and an implementation roadmap.

Two facts drove this pass:

1. **Most M06.1 design documents already existed** in the repository (committed, not untracked). They were reviewed, corrected against the live codebase, and aligned with each other rather than blindly regenerated.
2. **The Inventory database schema already exists** (changesets `v1.0.0/23`–`v1.0.0/32`, wired into `db.changelog-master.xml`, covered by `InventoryDatabaseMigrationIntegrationTest`). The brief stated that Inventory was unimplemented and no migrations existed. That premise is stale: **the schema is ahead of the code**, with zero Inventory Java classes and M04 RBAC still limited to `TENANT`/`BRANCH`. This is documented as **ADR-0017** and is the main unresolved situation requiring the user's decision.

No code or migrations were added, modified, or deleted in this pass.

## 5. Main Architecture Decisions (ADR-0011 – ADR-0017)

| ADR | Decision |
|---|---|
| **0011** | `Warehouse` belongs to `inventory`, with nullable `branch_id` so central hubs need no fake branch; at most one default warehouse per branch |
| **0012** | Flat `StockLocation` per warehouse (`STORAGE`, `PICKING`, `RECEIVING_DOCK`, `DAMAGED`, `QUARANTINE`), one auto-created default `STORAGE` location, mandatory `location_id` everywhere; no recursive hierarchy |
| **0013** | Immutable header+line ledger; two projections (`inventory_balances` per location, `inventory_warehouse_stocks` per warehouse); negative stock disabled by default; rebuildable from the ledger |
| **0014** | Reservations are a separate aggregate with **no ledger rows**; transfers are two-step (`TRANSFER_OUT` at dispatch with destination `in_transit`, `TRANSFER_IN` at receipt with good/damaged/shortage split); dispatched transfers cannot be cancelled |
| **0015** | Moving WAC per `(tenant, warehouse, variant)`, `NUMERIC(15,4)` unit cost / `NUMERIC(18,4)` value, `HALF_UP`, zero-depletion reset |
| **0016** | `WAREHOUSE` RBAC scope with no `BRANCH` inheritance; 20 additive `inventory.*` permissions; live API envelope/error shapes; shared idempotency table; `ON DELETE RESTRICT` |
| **0017** | Pre-existing schema changesets `23`–`32` accepted as delivered M06.2 schema; docs aligned to them; Java-side gaps explicitly listed |

Additional refinements made in this pass:

- Ledger posting has **no `DRAFT` state**; `InventoryPostingStatus` persists only `POSTED`, and operational documents own draft states.
- `RESERVATION`, `RESERVATION_RELEASE`, `RESERVATION_CONSUMPTION` are explicitly **rejected** as movement types (breaks ledger parity, duplicates reserved state, double-counts consumption).
- Quantity semantics (`physical`, `sellable`, `reserved`, `available`, `in-transit`, `damaged`, `quarantined`, `staging`) documented as one canonical table with arithmetic invariants.
- Denied-access behavior for tenants/branches/warehouses specified, including the empty-permitted-set trap.
- API DTO catalog added; `description` of tenant header removed.

## 6. Risks and Open Questions

### 6.1 Risks

| Risk | Impact | Mitigation / status |
|---|---|---|
| **Schema ahead of code** (migrations 23–32 committed, no Java) | A deploy runs Inventory tables and an inert 20-permission seed; `Permissions.ALL_PERMISSIONS` still excludes them, so `OWNER` cannot actually use them and `@PreAuthorize` cannot reference them | ADR-0017; M06.3 must add the constants together with `RoleScopeType.WAREHOUSE`. Do not ship the seed alone as a security change |
| Migrations applied to a populated M04/M05 database were not verified | `v1.0.0/31` drops and recreates RBAC `CHECK` constraints; a legacy inconsistent row would fail the migration | Remaining M06.2 verification item; run against a populated snapshot before the next deploy |
| Append-only ledger is application-enforced only | A bug or manual SQL could `UPDATE`/`DELETE` ledger rows | Repository design (no update/delete methods), ArchUnit/application tests in M06.4, optional DB privilege hardening in M06.11 |
| WAC per warehouse vs. tenant-wide reporting | Cross-warehouse consolidated valuation must aggregate, and transfer cost blending can shift margin between branches | Documented; acceptable for MVP. FIFO/lot layers deferred and can use existing `unitCost`/`wacAfter` snapshots |
| `BRANCH` stock-read bridge | Could accidentally widen into write access if implemented as inheritance | Explicitly limited to read endpoints and `Warehouse.branchId` match; writes always require `TENANT`/`WAREHOUSE` |
| Reservation TTL job scans many tenants | Long-running scheduler, lock contention | Per-tenant `TenantExecutionTemplate` batches, `SKIP LOCKED`/pessimistic locks, bounded batches |

### 6.2 Unresolved questions (require product/owner decision)

1. **Keep or revert the existing schema changesets?** They contradict the "design-only" brief but are committed and tested. This pass keeps them and documents the gap; a revert would need explicit approval and a migration rollback plan.
2. **Should existing tenants' `ADMIN` / `WAREHOUSE_MANAGER` system roles receive the new inventory permissions automatically?** Current design follows M04 conservatism: new tenants get template defaults, existing tenants get them on `OWNER` only, custom roles never touched.
3. **Is `WAREHOUSE_MANAGER`'s default scope switched from `BRANCH` to `WAREHOUSE` for new tenants?** Existing assignments are preserved either way; the template change is proposed but not approved.
4. **Cost visibility for `MANAGER`**: the matrix marks `inventory.costs.read` "optional / no default"; needs a product decision.
5. **Negative stock**: kept configurable and disabled; no tenant policy UI is designed in M06.
6. **Generic stock issue** (`SALE_ISSUE` only today): if non-sales consumption (internal use, samples, production) is required, a `STOCK_ISSUE` movement type should be added before the enum is frozen in M06.4.

### 6.3 Architectural inconsistencies found (and their disposition)

- **Delete policy**: legacy `database-design.md` sketches `ON DELETE CASCADE`; M04/M05 and all M06 FKs use `RESTRICT`. M06 follows `RESTRICT`; legacy doc left unchanged but flagged.
- **API envelope**: legacy `api-conventions.md` pagination/error shapes differ from implemented `PageResponse`/`ProblemDetail`. M06 follows the implementation.
- **Technology baseline**: `backend-architecture.md` and `ADR-011` cite Spring Boot 3.4.x / Gradle 8.10.2; the build is Spring Boot 4.2.0 / Gradle 9.9.1. Outside M06 scope; noted only.
- **Roadmap has two Milestone-2/3/4 numbering schemes** (old "M2 catalog / M3 inventory" legacy sections plus the current M01–M06 scheme). The current scheme is authoritative; legacy sections were left as historical reference.
- **ADR numbering collision**: `architecture-decisions.md` uses `ADR-001`–`ADR-016` (legacy), while `decisions/` and this milestone use `ADR-0005`–`ADR-0017`. `ADR-011` (legacy Spring Boot version) and `ADR-0011` (Warehouse placement) are different records. A note in `06-inventory-decisions.md` disambiguates the series; no historical record was renumbered.
